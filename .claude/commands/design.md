# 設計コマンド

要件を受け取って、実装前の詳細な設計を行います。実装は行いません。

## 設計フロー

### 1. 要件分析
- ユーザーの要件を明確化
- 機能要件と非機能要件を整理
- 不明点があれば質問

### 2. アーキテクチャ参照
- `docs/baseball-project-architecture.md` を読み込み
- 既存のアーキテクチャパターンを確認
- `docs/coding-standards.md` を読み込み
- プロジェクトの設計方針を把握

### 3. 設計書作成

以下の観点で設計を行います（要件に応じて必要なものを選択）：

#### 3.1 アーキテクチャ設計
- レイヤー構成（Controller/Service/Repository/Entity）
- コンポーネント間の依存関係
- データフロー
- 既存システムとの整合性

#### 3.2 データベース設計
- テーブル設計（新規/変更）
- カラム定義
- インデックス
- リレーション
- マイグレーション方針

#### 3.3 API設計
- エンドポイント定義
- HTTPメソッド
- リクエスト/レスポンス形式
- エラーハンドリング
- バリデーション

#### 3.4 UI/UX設計
- 画面レイアウト
- コンポーネント構成
- ユーザーフロー
- レスポンシブ対応
- アクセシビリティ

#### 3.5 セキュリティ設計
- 認証/認可
- 入力検証
- XSS/CSRF/SQLインジェクション対策
- 機密情報の取り扱い

#### 3.6 パフォーマンス設計
- キャッシュ戦略
- N+1問題対策
- ページネーション
- 非同期処理

### 4. 技術選定
- 使用するライブラリ/フレームワーク
- 選定理由
- 代替案との比較

### 5. 実装計画
- ファイル構成
- 実装順序
- 見積もり工数
- リスク項目

### 6. 設計ドキュメント出力

設計内容をMarkdown形式で出力します：

```markdown
# [機能名] 設計書

## 1. 概要
機能の目的と概要

## 2. 要件
### 機能要件
- 要件1
- 要件2

### 非機能要件
- パフォーマンス
- セキュリティ
- 保守性

## 3. アーキテクチャ設計
### システム構成
### データフロー

## 4. データベース設計
### テーブル定義
### ER図

## 5. API設計
### エンドポイント一覧

## 6. UI/UX設計
### 画面遷移
### コンポーネント構成

## 7. セキュリティ設計
### 対策項目

## 8. 実装計画
### ファイル構成
### 実装順序

## 9. リスクと対策
### 想定リスク
### 対策

## 10. 次のステップ
- 実装時の注意事項
- テスト観点
```

### 7. ユーザー承認
設計内容をユーザーに提示し、承認を得る（y/n）

## 使用方法

### 基本的な使い方
```
/design Google AdSense統合機能
```

### 詳細な要件を指定
```
/design 有料プラン機能
- 月額500円のプレミアムプラン
- 詳細統計データの閲覧
- データのCSVエクスポート
- 広告非表示
```

### 特定の設計のみ
```
/design データベース設計のみ: 試合結果テーブルに天気情報を追加
```

## オプション機能

### 設計ドキュメントの保存
承認後、設計ドキュメントを `docs/designs/` に保存するか確認します。

### 実装への移行
設計が承認されたら、以下のコマンドで実装に進めます：
```bash
# シンプルに実装のみ
/implement この設計に基づいて実装

# 1人で設計〜レビューまで全自動
/auto-implement この設計に基づいて実装

# 専門家チームで高品質実装
/team この設計に基づいて実装
```

## コマンド選択ガイド

| やりたいこと | コマンド |
|-------------|---------|
| 設計だけ欲しい | `/design`（これ） |
| 設計を3案比較したい | `/parallel-design` |
| 設計→実装まで一気に | `/auto-implement` |
| 専門家チームで設計→実装 | `/team` |

## 注意事項

- このコマンドは設計のみを行い、実装はしません
- 実装も含めて自動で行いたい場合は `/auto-implement` を使用
- 専門家チームで高品質に開発したい場合は `/team` を使用
- 設計の妥当性を検証し、問題があれば指摘
- 既存のアーキテクチャとの整合性を重視
- 言語: 思考は英語、アウトプットは日本語
