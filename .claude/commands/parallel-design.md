# 並列設計コマンド

3人の設計エージェントが並列で設計案を作成し、評価者が最適な設計を選択、レビューエージェントが洗練させます。

## ワークフロー

```
要件入力
   ↓
┌──┴──┐ 並列起動
│     │
設計者1 設計者2 設計者3
│     │     │
└──┬──┴─────┘
   ↓
 評価者（ベスト選択）
   ↓
レビュー者（修正繰り返し）
   ↓
最終設計完成
```

## 実行フロー

### 1. 要件確認
- ユーザーから要件を受け取る
- 不明点があれば質問

### 2. 並列設計（3エージェント同時起動）
**Taskツールで3つのエージェントを並列起動:**

```javascript
// 3つのTask呼び出しを1つのメッセージで実行
Task1: 設計者A - アーキテクチャ重視の設計
Task2: 設計者B - パフォーマンス重視の設計
Task3: 設計者C - 保守性重視の設計
```

各設計者は以下を作成：
- アーキテクチャ設計
- データベース設計
- API設計
- UI/UX設計
- セキュリティ設計
- 実装計画

### 3. 評価・選択
評価エージェントが以下の観点で評価：

#### 評価基準
- ✅ アーキテクチャの適切性
- ✅ スケーラビリティ
- ✅ セキュリティ
- ✅ パフォーマンス
- ✅ 保守性
- ✅ 実装の現実性
- ✅ コスト

#### 選択方法
- 各設計案にスコアリング
- ベスト設計を選択
- または複数の良い部分を統合

### 4. レビュー・洗練
レビューエージェントが選択された設計を精査：

#### レビュー観点
- アーキテクチャの整合性
- 既存システムとの互換性（`docs/baseball-project-architecture.md`参照）
- コーディング規約との整合性（`docs/coding-standards.md`参照）
- セキュリティ脆弱性
- パフォーマンスボトルネック
- エッジケースの考慮

#### 修正プロセス
1. 問題点を指摘
2. 改善案を提示
3. 設計を修正
4. 再レビュー
5. 問題がなくなるまで繰り返し（最大3回）

### 5. 最終確認
- 最終設計をユーザーに提示
- 承認を得る（y/n）

### 6. ドキュメント保存
承認後、設計ドキュメントを `docs/designs/[機能名]-design.md` に保存

## 使用方法

### 基本
```
/parallel-design 有料プラン機能
```

### 詳細要件付き
```
/parallel-design ユーザー認証機能
- OAuth 2.0対応
- Google/Twitter連携
- JWT認証
- リフレッシュトークン
```

### 既存機能の改善
```
/parallel-design 検索機能のパフォーマンス改善
```

## Taskツール使用例

```markdown
# メインスレッドで実行

## 1. 並列で3エージェントを起動

<Task subagent_type="general-purpose">
設計者A: [要件] に対してアーキテクチャ重視の設計を作成。
- docs/baseball-project-architecture.md を参照
- docs/coding-standards.md を参照
- アーキテクチャ設計、DB設計、API設計、UI設計を含む
- マークダウン形式で設計書を返す
</Task>

<Task subagent_type="general-purpose">
設計者B: [要件] に対してパフォーマンス重視の設計を作成。
（同様の指示）
</Task>

<Task subagent_type="general-purpose">
設計者C: [要件] に対して保守性重視の設計を作成。
（同様の指示）
</Task>

## 2. 3つの設計案を受け取る

## 3. 評価エージェントを起動

<Task subagent_type="general-purpose">
評価者: 以下の3つの設計案を評価し、最適な設計を選択。
または複数の良い点を統合した設計案を作成。

[設計案A]
[設計案B]
[設計案C]

評価基準: アーキテクチャ、スケーラビリティ、セキュリティ、
パフォーマンス、保守性、実装の現実性、コスト
</Task>

## 4. レビューエージェントを起動

<Task subagent_type="general-purpose">
レビュー者: 選択された設計案をレビュー。
問題点を指摘し、改善案を提示。
最大3回まで修正を繰り返す。
</Task>

## 5. 最終設計をユーザーに提示
```

## 注意事項

- 並列実行には時間がかかる場合があります（3エージェント同時実行）
- 各エージェントは独立して動作します
- 評価は客観的な基準に基づきます
- レビューは最大3回まで繰り返します
- 言語: 思考は英語、アウトプットは日本語

## 設計の原則

### docs参照必須
- `docs/baseball-project-architecture.md` - 既存アーキテクチャ
- `docs/coding-standards.md` - コーディング規約

### 重視する観点
1. **既存システムとの整合性**
2. **セキュリティ**
3. **スケーラビリティ**
4. **保守性**
5. **実装の現実性**

## 設計者の役割分担

### 設計者A（アーキテクチャ重視）
- クリーンアーキテクチャ
- レイヤー分離
- SOLID原則
- デザインパターン活用

### 設計者B（パフォーマンス重視）
- データベース最適化
- キャッシュ戦略
- 非同期処理
- N+1問題対策

### 設計者C（保守性重視）
- コードの可読性
- テスタビリティ
- ドキュメント完備
- エラーハンドリング

これにより多角的な視点で最適な設計が得られます。

## コマンド選択ガイド

| やりたいこと | コマンド |
|-------------|---------|
| 設計だけ（1人） | `/design` |
| 設計を3案比較（5人） | `/parallel-design`（これ） |
| 設計→実装まで自動（1人） | `/auto-implement` |
| 専門家チームで設計→実装（10人） | `/team` |
| 設計3案→実装3案→統合（25人） | `/parallel-auto` |
