# 最強チーム開発モード

10人の専門エージェントが役割分担して、要件定義から実装・レビュー・テスト・ドキュメントまでを一気通貫で完成させます。

## チーム構成

```
┌─────────────────────────────────────────┐
│            最強開発チーム（10人）          │
├─────────────────────────────────────────┤
│                                         │
│  👔 PM（プロマネ）     要件整理・タスク分割  │
│  🏗️ アーキテクト       設計・技術選定       │
│  ☕ バックエンドエンジニア  Java/Spring Boot │
│  🎨 フロントエンドエンジニア  Vue.js/CSS    │
│  🔒 セキュリティ審査官   脆弱性監査         │
│  🧪 QAエンジニア       テスト設計・実行     │
│  👹 鬼レビュアー       容赦ないコードレビュー │
│  ✨ リファクタリスト    最適化・美化         │
│  🔗 インテグレーター    統合・整合性確認     │
│  🎯 テックリード       最終判断・品質保証    │
│                                         │
└─────────────────────────────────────────┘
```

## 実行フロー

### フェーズ1: 要件定義・設計

#### 1.1 PM（プロマネ）
```
<Task subagent_type="general-purpose">
PM: 以下の要件を分析し、実装タスクを整理する。

【要件】
$ARGUMENTS

【PMの仕事】
1. 要件を明確化（曖昧な部分を具体化）
2. ユーザーストーリーを作成
3. 受け入れ基準を定義
4. タスクを実装可能な単位に分割
5. 優先順位をつける
6. リスク・注意点を洗い出す

【出力形式】
- ユーザーストーリー一覧
- 受け入れ基準
- タスク分割（バックエンド/フロントエンド別）
- リスク・注意点
</Task>
```

#### 1.2 アーキテクト
```
<Task subagent_type="general-purpose">
アーキテクト: PMの要件整理に基づいて、技術設計を行う。

【参照必須】
- docs/baseball-project-architecture.md
- docs/coding-standards.md

【アーキテクトの仕事】
1. 既存アーキテクチャとの整合性を確認
2. 技術選定と根拠
3. データベース設計（テーブル定義、ER図）
4. API設計（エンドポイント、リクエスト/レスポンス）
5. コンポーネント設計（フロントエンド）
6. シーケンス図（主要フロー）
7. 変更が必要な既存ファイルのリスト

【出力形式】
- アーキテクチャ設計書
- DB設計
- API仕様
- コンポーネント設計
- 変更ファイル一覧
</Task>
```

#### 1.3 ユーザー承認
設計をユーザーに提示し、承認を得る（y/n）

### フェーズ2: 並列実装

```
- 既存パターンに完全準拠
- PreparedStatementによるSQL安全性
- 適切な例外処理
- ログ出力
- JavaDoc
</Task>

<Task subagent_type="general-purpose">
フロントエンドエンジニア: 設計に基づいてVue.js/Bootstrap Vueの実装を行う。

【参照必須】
- docs/coding-standards.md
- 既存コンポーネントのパターン

【実装範囲】
- Vueコンポーネント
- API連携（Axios）
- CSS/スタイリング
- レスポンシブ対応
- ローディング・エラー表示

【実装原則】
- 既存コンポーネントのパターン踏襲
- Bootstrap Vue活用
- モバイルファースト
- アクセシビリティ配慮
</Task>
```

### フェーズ3: 多角的レビュー（3人並列起動）

```
<Task subagent_type="general-purpose">
セキュリティ審査官: 実装されたコードのセキュリティ監査を行う。

【監査項目】
1. SQLインジェクション
2. XSS（クロスサイトスクリプティング）
3. CSRF
4. コマンドインジェクション
5. 認証・認可の不備
6. 機密情報のハードコード
7. 入力値バリデーション不足
8. OWASP Top 10準拠チェック

【出力形式】
- 🚨 重大: 即座に修正が必要
- ⚠️ 警告: 修正推奨
- 💡 推奨: セキュリティ強化の提案
</Task>

<Task subagent_type="general-purpose">
鬼レビュアー: 実装されたコードを容赦なくレビューする。

【レビュー観点】
1. コーディング規約準拠（docs/coding-standards.md）
2. アーキテクチャ整合性（docs/baseball-project-architecture.md）
3. SOLID原則違反
4. DRY原則違反（コード重複）
5. 命名の適切性
6. メソッドの責務分離
7. エラーハンドリングの網羅性
8. エッジケースの考慮
9. N+1問題
10. 不要なコード・コメント

【レビュースタイル】
- 妥協しない。問題は全て指摘する
- 具体的な改善コードを提示する
- 良い点も認める（モチベーション維持）

【出力形式】
- 🚨 MUST FIX: 必ず修正
- ⚠️ SHOULD FIX: 修正すべき
- 💡 NICE TO HAVE: あれば良い
- ✅ GOOD: 良い実装
</Task>

<Task subagent_type="general-purpose">
QAエンジニア: テスト観点でコードを検証する。

【QAの仕事】
1. テストケース設計
   - 正常系
   - 異常系
   - 境界値
   - エッジケース
2. 手動テスト手順書の作成
3. ビルド確認（./gradlew build）
4. コンパイルエラーチェック
5. 既存機能への影響確認（回帰テスト観点）

【出力形式】
- テストケース一覧（表形式）
- テスト実行結果
- バグ報告（あれば）
- テストカバレッジ改善提案
</Task>
```

---

### フェーズ4: 修正・統合

#### 4.1 リファクタリスト
```
<Task subagent_type="general-purpose">
リファクタリスト: レビュー指摘を反映し、コードを最適化する。

【入力】
- セキュリティ審査官の指摘
- 鬼レビュアーの指摘
- QAエンジニアの指摘

【リファクタリストの仕事】
1. 🚨 MUST FIX を全て修正
2. ⚠️ SHOULD FIX を可能な限り修正
3. コードの重複排除
4. 可読性向上
5. パフォーマンス最適化
6. 不要なコード削除

【原則】
- 機能を壊さない
- 既存パターンに準拠
- シンプルさを保つ（過度な抽象化は避ける）
</Task>
```

#### 4.2 インテグレーター
```
<Task subagent_type="general-purpose">
インテグレーター: バックエンドとフロントエンドを統合し、整合性を確認する。

【インテグレーターの仕事】
1. API接続の確認（エンドポイント・パラメータ一致）
2. データフローの検証（リクエスト→処理→レスポンス→表示）
3. エラーレスポンスの整合性
4. CORS設定確認
5. ビルド確認（./gradlew build）
6. フロントエンドビルド確認（npm run build）
7. 統合時の競合解決
8. 動作確認チェックリスト作成

【出力形式】
- 統合結果レポート
- 動作確認チェックリスト
- 未解決の問題（あれば）
</Task>
```

---

### フェーズ5: 最終判定

#### 5.1 テックリード
```
<Task subagent_type="general-purpose">
テックリード: 全工程の成果物を最終レビューし、品質を保証する。

【テックリードの仕事】
1. 全体アーキテクチャの妥当性確認
2. コード品質の最終チェック
3. セキュリティ対策の十分性確認
4. パフォーマンス懸念の確認
5. 本番環境デプロイの準備度チェック
6. 残課題の整理

【判定基準】
- ✅ SHIP IT: デプロイ可能
- ⚠️ CONDITIONAL: 軽微な修正後にデプロイ可能
- 🚨 HOLD: 重大な問題があり、修正が必要

【出力形式】
## 最終判定: [SHIP IT / CONDITIONAL / HOLD]

### 品質スコア
- 設計: X/10
- 実装: X/10
- セキュリティ: X/10
- テスト: X/10
- 保守性: X/10
- 総合: X/50

### 判定理由
[詳細な理由]

### 残課題（あれば）
[対応すべき課題のリスト]

### 次のステップ
[推奨アクション]
</Task>
```

## 既存コマンドとの比較

| コマンド | 人数 | 設計 | 実装 | レビュー | テスト | 特徴 |
|---------|------|------|------|---------|--------|------|
| `/implement` | 1 | ❌ | ✅ | ❌ | ❌ | 最速・最小 |
| `/auto-implement` | 1 | ✅ | ✅ | セルフ | 簡易 | バランス型 |
| `/parallel-design` | 5 | ✅✅✅ | ❌ | ✅ | ❌ | 設計特化 |
| `/parallel-implement` | 18 | ❌ | ✅✅✅ | ✅✅ | ❌ | 実装特化 |
| `/parallel-auto` | 25 | ✅✅✅ | ✅✅✅ | ✅✅ | ✅ | 全部盛り |
| **`/team`** | **10** | **✅** | **✅✅** | **✅✅✅** | **✅** | **専門家集団** |

### `/team` の強み
- **専門性**: 各メンバーが異なる専門分野を持つ（セキュリティ、QA、リファクタ等）
- **効率**: 並列実行で高速（実装2人並列、レビュー3人並列）
- **多角的品質保証**: セキュリティ・コード品質・テストの3軸レビュー
- **実践的**: 実際の開発チームに近い構成

## エージェント起動スケジュール

```
フェーズ1（順次）: PM → アーキテクト           = 2人
フェーズ2（並列）: BE + FE                    = 2人同時
フェーズ3（並列）: セキュリティ + 鬼レビュー + QA = 3人同時
フェーズ4（順次）: リファクタリスト → インテグレーター = 2人
フェーズ5（順次）: テックリード                 = 1人
                                          合計: 10人
```

### 並列度
- 最大同時起動: 3人（フェーズ3）
- 総エージェント数: 10人
- 推定実行時間: 15-40分

---

## 注意事項

- **承認ポイント**: フェーズ1の設計完了時に1回のみ
- **コスト**: `/parallel-auto`（25人）より効率的
- **品質**: 専門家による多角的レビューで高品質を保証
- **言語**: 思考は英語、アウトプットは日本語
- **docs参照**: 全エージェントが `docs/coding-standards.md` と `docs/baseball-project-architecture.md` を参照

---

## CONDITIONAL/HOLD時の対応

テックリードの判定が **CONDITIONAL** または **HOLD** の場合:

1. 指摘事項をリファクタリストが修正
2. 再度テックリードが最終判定
3. SHIP IT になるまで繰り返し（最大2回）

---

## 推奨ケース

### `/team` を使うべき場合
- ✅ 中〜大規模の新機能開発
- ✅ セキュリティが重要な機能
- ✅ フロント・バック両方の変更がある機能
- ✅ 本番デプロイ前の品質保証が必要な場合

### 他のコマンドで十分な場合
- ❌ バグ修正 → `/implement`
- ❌ 小さなUI変更 → `/auto-implement`
- ❌ 設計のみ → `/parallel-design`
- ❌ 最高品質を求める大規模開発 → `/parallel-auto`
