# 実装コマンド

設計が既に完了している前提で、実装のみを行います。

## 実行フロー

### 1. 実装内容の確認
- 何を実装するのか確認
- 既存の設計ドキュメントがあれば参照
- 必要に応じて `docs/baseball-project-architecture.md` と `docs/coding-standards.md` を確認

### 2. ユーザー承認
実装内容を簡潔に確認し、承認を得る（y/n）

### 3. 実装開始（承認後）

#### 3.1 タスク管理
TodoWriteツールでタスクを管理：
- 実装するファイル/機能ごとにタスク化
- 進捗を可視化

#### 3.2 コーディング
以下に従って実装：
- `docs/coding-standards.md` のコーディング規約を遵守
- `docs/baseball-project-architecture.md` のアーキテクチャパターンに従う
- セキュリティベストプラクティスを適用
- 適切なコメントを追加

#### 3.3 実装内容
以下を実装：
- Entity（必要に応じて）
- Repository（必要に応じて）
- Service
- Controller/API
- Vue コンポーネント（UI変更の場合）
- スタイル（UI変更の場合）

### 4. 実装完了報告
以下を含むサマリーを報告：
- 実装したファイル一覧
- 主な実装内容
- 注意事項
- 次のステップの提案

## 使用方法

### 設計に基づいて実装
```
/implement /designで提案した設計に基づいてユーザー認証機能を実装
```

### 簡単な実装（設計不要）
```
/implement Google AdSenseスクリプトを検索結果の下に追加
```

### 特定ファイルの修正
```
/implement SearchBaseball.vueに年度フィルタを追加
```

## ワークフロー例

### パターン1: 設計 → 実装
```bash
# 1. 設計
/design 有料プラン機能

# 2. 設計レビュー・承認

# 3. 実装
/implement この設計に基づいて実装

# 4. テスト（必要に応じて）
/quick-test

# 5. レビュー（必要に応じて）
/review
```

### パターン2: 小さな変更（実装のみ）
```bash
# 実装のみでOK
/implement フッターに会社情報を追加

# 必要に応じてテスト
/quick-test
```

## 実装の原則

### 1. コーディング規約
- インデント: スペース2個（Vue）、4個（Java）
- 命名規則: キャメルケース（Java）、ケバブケース（Vue）
- コメント: 複雑なロジックには必ず説明を追加

### 2. アーキテクチャパターン
- レイヤードアーキテクチャを維持
- Controller → Service → Repository の依存関係を守る
- ビジネスロジックはServiceに集約

### 3. セキュリティ
- 入力値は必ずバリデーション
- SQLインジェクション対策（PreparedStatement使用）
- XSS対策（エスケープ処理）
- 機密情報のハードコード禁止

### 4. エラーハンドリング
- 適切な例外処理
- ユーザーフレンドリーなエラーメッセージ
- ログ出力

### 5. パフォーマンス
- N+1問題の回避
- 不要なループの削減
- 適切なインデックス使用

## 実装後の推奨アクション

実装完了後、以下のコマンドを使って品質を確保：

```bash
# テスト実行
/quick-test

# コードレビュー
/review
```

### より高品質を求める場合
```bash
# 全自動（1人で設計〜レビューまで）
/auto-implement

# 専門家チーム（10人で高品質開発）
/team
```

## 注意事項

- このコマンドは実装のみを行います
- リファクタリング、テスト、レビューは含まれません
- それらも含めたい場合は `/auto-implement` を使用
- 専門家チームで高品質に開発したい場合は `/team` を使用
- 実装中に設計上の問題を発見した場合は報告
- 言語: 思考は英語、アウトプットは日本語
